# Time Tracker — Design

Date: 2026-10-08
Status: superseded by `2026-10-10-better-hours-design.md`

## 1. Goal

A calendar-style time tracker. You block time by hand on a calendar, or start and stop a timer and fill in the details later. It runs as a website (online) and as a macOS desktop app (local-first, syncing periodically or on demand). The desktop app shows the same UI as the website plus a menubar popover for quick timer control.

## 2. Scope

In scope for the first version:

- Sign-up and login with email and password; each user sees only their own data.
- Time blocks with title, notes, optional project, and tags.
- Week and day calendar: create a block by dragging, move and resize it, click to edit details.
- Timer: start, stop, continue the last block, or start a new one.
- Website that reads and writes straight to the server.
- macOS desktop app with a local database, usable offline after the first login.
- Sync every 5 minutes, on window focus, at launch, and from a "Sync now" button.
- Menubar: elapsed time in the bar, popover with start/stop, continue/new, current block time, and today's total.

Out of scope for now: teams and sharing, reports and export, billing rates, idle detection, reminders, OAuth login, password-reset and verification emails, offline use of the website, Windows and Linux builds, mobile, live push between devices, and purging of deletion markers.

## 3. Decisions

Rows marked "you" were chosen during brainstorming. Rows marked "default" are my picks and are open to challenge.

| Topic | Decision | Chosen by |
|---|---|---|
| Users | Multiple separate users, no teams | you |
| Database | Postgres on Neon, accessed through Prisma | you |
| Auth | Better Auth, self-hosted, email + password | you |
| Web data | Online-only, no local copy in the browser | you |
| Block fields | Title, notes, project, tags | you |
| Desktop login | Required before first use | you (simpler option) |
| Sync method | Push/pull of changed rows, last edit wins per row | you |
| Server framework | Hono on Node | default |
| Repo layout | pnpm workspace: client, server, shared | default |
| Calendar component | FullCalendar (timeGrid + interaction plugins) | default |
| Desktop local database | SQLite through `tauri-plugin-sql`, driven from TypeScript | default |
| Menubar UI | Small frameless window showing a React route, not a native menu | default |
| "Continue" meaning | Starts a new block copying the last block's title, project, and tags | default |
| Tags storage | Array of tag ids on the block, not a join table | default |

## 4. Architecture

```
time-tracker/
  apps/
    client/            Vite + React + TypeScript + Tailwind + shadcn/ui
      src/             shared UI for web and desktop
      src-tauri/       Tauri v2 shell: windows, tray, SQLite plugin, keychain
    server/            Hono API, Better Auth, Prisma, sync endpoint
  packages/
    shared/            zod schemas, entity types, sync payload types, pure logic
```

```
 Website (browser)                 Desktop app (Tauri)
 ┌──────────────┐                  ┌──────────────────────────────┐
 │ React UI     │                  │ React UI (main + tray window)│
 │ HttpStore    │                  │ LocalStore ── SQLite         │
 └──────┬───────┘                  │ SyncController               │
        │ REST, cookie             └──────┬───────────────────────┘
        │                                 │ POST /api/sync, bearer token
        └────────────┬────────────────────┘
                     ▼
              Hono server ── Prisma ── Neon Postgres
```

The UI never knows which side it is on. It talks to one interface, `TimeStore` (section 6), which has two implementations: `HttpStore` for the website and `LocalStore` for the desktop. The implementation is picked once at startup by checking for the Tauri runtime.

`HttpStore` uses plain REST: `GET /api/blocks?from=&to=`, `PUT /api/blocks/:id` (create or update), `DELETE /api/blocks/:id`, and the same three for `/api/projects` and `/api/tags`. `LocalStore` uses SQLite, and only `SyncController` calls `POST /api/sync`. Better Auth serves `/api/auth/*`.

The website is a static build served from the same domain as the API (`/api/*` proxied to the server), so the session cookie is first-party.

Rust stays small. It owns the tray icon and its title text, the two windows, the SQLite plugin registration and migrations, and the keychain commands. All data logic is TypeScript.

## 5. Data model

All ids are UUIDv7 generated by whichever client creates the row. All times are UTC instants; the UI displays them in the device time zone.

**Project**: `id`, `userId`, `name`, `color`.

**Tag**: `id`, `userId`, `name`.

**TimeBlock**: `id`, `userId`, `title` (may be empty), `notes`, `projectId` (nullable), `tagIds` (array of tag ids), `startAt`, `endAt` (null means the timer is running).

Every table also carries the sync columns:

- `updatedAt`: when the row was last edited, set by the client that made the edit.
- `deletedAt`: null, or the time the row was deleted. Deleted rows are kept as markers so the deletion reaches other devices.
- `rev`: a number the server assigns from one global sequence on every write. Server only.

The desktop SQLite schema mirrors these tables (with `tagIds` as JSON text and no `rev`), plus a `dirty` flag per row and a one-row `sync_state` table holding the last `cursor` and `lastSyncedAt`.

Rules:

- `endAt`, when set, must be after `startAt`.
- A user has at most one running block.
- Blocks may overlap; the calendar shows them side by side.
- A block that references a deleted project or tag simply shows without it.

## 6. The store interface

This is the one interface every screen depends on, so its shape is fixed here.

```ts
interface TimeStore {
  listBlocks(range: { from: Date; to: Date }): Promise<TimeBlock[]>;
  getRunningBlock(): Promise<TimeBlock | null>;
  saveBlock(block: TimeBlockInput): Promise<TimeBlock>; // create or update by id
  deleteBlock(id: string): Promise<void>;

  startTimer(seed?: TimerSeed): Promise<TimeBlock>;     // stops any running block first
  stopTimer(): Promise<TimeBlock | null>;

  listProjects(): Promise<Project[]>;
  saveProject(project: ProjectInput): Promise<Project>;
  deleteProject(id: string): Promise<void>;

  listTags(): Promise<Tag[]>;
  saveTag(tag: TagInput): Promise<Tag>;
  deleteTag(id: string): Promise<void>;

  subscribe(listener: () => void): () => void;          // fires on any data change
}

type TimerSeed = Pick<TimeBlock, 'title' | 'projectId' | 'tagIds'>;
```

Notes on the shape:

- It is async because both backends are I/O (HTTP, and the SQLite plugin's IPC). Screens consume it through TanStack Query, so components stay synchronous to write.
- `saveBlock` is an upsert keyed by a client-generated id. That gives the website and the desktop the same create/update semantics and makes retries safe.
- `subscribe` is how the UI learns about changes it did not make: a sync pull, or an edit in the other desktop window. `HttpStore` fires it after its own writes only.
- Totals are not on the interface. `totalForDay(blocks, day, now)` is a pure function in `packages/shared`; it clips blocks that cross midnight and counts a running block up to `now`.

Sync is deliberately separate, and exists only on desktop:

```ts
interface SyncController {
  syncNow(): Promise<SyncResult>;
  getStatus(): SyncStatus; // idle | syncing | error, plus lastSyncedAt
  subscribe(listener: () => void): () => void;
}
```

## 7. Timer behaviour

- **Start** creates a block with `startAt = now` and `endAt = null`. If a block is already running it is stopped first.
- **Stop** sets `endAt = now` on the running block.
- **Continue** starts a new block seeded with the title, project, and tags of the most recently ended block. It does not stretch the old block across the gap, so the calendar stays truthful.
- **New** starts a blank block. Details are added later from the calendar or the popover's title field.
- The running block appears on the calendar growing toward the current time.

## 8. Sync

One call does both directions.

```
POST /api/sync
request:  { cursor: string | null, changes: { projects: [], tags: [], blocks: [] } }
response: { cursor: string,        changes: { projects: [], tags: [], blocks: [] } }
```

**Server, in one transaction:**

1. Take a per-user lock, so `rev` values for one user become visible in order and a pull can never skip a row.
2. For each pushed row: accept it if the row is new or its `updatedAt` is later than the stored one, otherwise ignore it. An `updatedAt` in the future is clamped to the server's current time. Each accepted row gets the next `rev`.
3. If the user now has more than one running block, keep the latest-started one running and end each older one at the start of the next.
4. Return every row for the user with `rev` greater than the request's `cursor`, and the new `cursor`.

Writes from the website go through the same lock and `rev` assignment, which is how they reach the desktop.

**Desktop:**

1. Collect all rows with `dirty = 1` and send them with the stored cursor.
2. For each returned row: overwrite the local row, unless the local row is dirty and has a later `updatedAt`.
3. Clear `dirty` on each sent row whose `updatedAt` has not changed since it was sent (it may have been edited mid-sync).
4. Store the new cursor and `lastSyncedAt`, then fire `subscribe` listeners.

**Triggers:** at launch after login, every 5 minutes, when either window gains focus (at most once a minute), and from "Sync now" in the main window and the popover. Only one sync runs at a time.

**Known limits, accepted for this version:** if the same block is edited on two devices between syncs, the later edit replaces the earlier one entirely. "Later" is judged by device clocks, so a badly wrong clock can win unfairly. macOS may slow timers in hidden windows, so a periodic sync can be late; focus and manual triggers cover that.

## 9. Auth

- Better Auth with email and password, sessions stored in Postgres through its Prisma adapter.
- **Website:** session cookie, first-party because the API shares the site's domain.
- **Desktop:** the Tauri webview has a different origin, where cookies are unreliable, so the desktop uses Better Auth's bearer-token plugin. The token is kept in the macOS keychain behind three small Tauri commands (get, set, clear).
- Every server query is filtered by the session's `userId`; the sync endpoint ignores any `userId` in the payload.
- **Logout on desktop:** if unsynced changes exist, warn first. Local data is wiped on logout so a different account never sees it.
- **Expired session on desktop:** tracking continues locally, sync pauses, and the app asks you to log in again. Logging back in as the same user resumes sync with nothing lost.

## 11. Error handling

- **Website:** edits apply optimistically; on a failed request the change rolls back and a message appears.
- **Desktop writes** never touch the network, so they fail only on a local database error, which is shown as a blocking message.
- **Sync failure:** the status shows the error and the last successful time; the next trigger retries. Local data is never discarded because of a failed sync.
- **Validation:** the server validates every row with the shared zod schemas and rejects the whole sync call if any row is malformed, so a sync is all-or-nothing.

## 12. Testing

- **Unit (Vitest):** day totals including midnight clipping and a running block; the last-edit-wins merge rule; the single-running-timer rule.
- **Server integration:** the sync endpoint against a test Postgres, simulating two devices: both-create, edit conflict, delete on one and edit on the other, two running timers, a stale cursor.
- **LocalStore:** runs against an in-memory SQLite in tests by putting the database behind a two-method executor (`select`, `execute`), with the Tauri plugin as the production implementation.
- **Manual checklist:** tray title ticking with windows hidden, popover open and close, offline tracking then sync, logout wipe.

## 13. Build order

1. Server: Prisma schema, Better Auth, REST endpoints for blocks, projects, and tags.
2. Website: login, calendar, block editor, timer, using `HttpStore`.
3. Desktop shell: Tauri window around the same UI, SQLite, `LocalStore`, bearer login.
4. Sync: endpoint, `SyncController`, status UI.
5. Menubar: tray icon and title, popover window.

Each step leaves something usable: the website is complete after step 2, and the desktop app works offline after step 3.
