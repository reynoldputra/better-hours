# Better Hours — Design

Date: 2026-10-10
Status: draft, awaiting review
Supersedes: `2026-10-08-time-tracker-design.md` (the Tauri design)

## 1. Goal

Better Hours is a calendar-style time tracker. You block time by hand on a calendar, or start and stop a timer and fill in the details later.

It has two products that each work alone:

- A native macOS app with a main window and a menubar popover. It keeps everything in a local database and never needs an account or a network.
- A website with the same features, backed by a hosted database and OAuth login. Anyone can use it without the Mac app.

Linking the two is optional. A linked Mac app syncs its local database with the website account, so a timer started in one place shows up in the other.

The project is open source. One public instance of the website is hosted by the maintainer and open to anyone; others can self-host.

## 2. Phases

The work is split into three phases. Each one ships something usable, and the later ones can slip without reworking the earlier ones.

| Phase | Delivers | Done when |
|---|---|---|
| 1. Mac app, local only | Main window, menubar popover, projects and tags, light and dark themes, local SQLite | You can track a full week on one Mac with the network off |
| 2. Website | OAuth login, the same features in the browser, hosted database | A person with no Mac app can sign in and track a full week |
| 3. Linking and sync | Device linking from Settings, two-way sync, device management on the website | A timer started on the website appears in the menubar within about 20 seconds, and the reverse |

Phase 1 already stores the sync columns (section 5), so phase 3 adds a sync engine without migrating user data.

## 3. Scope

In scope:

- Time blocks with title, notes, optional project, and tags.
- Week and day calendar: create a block by dragging, move and resize it, click to edit.
- Timer: start, stop, continue the last block, or start a new one.
- Menubar: elapsed time in the bar, popover with start/stop, continue/new, the running block, and today's total.
- Totals: per day, this week, and per project for the week.
- Website: sign in with Google, then GitHub; every feature above except the menubar.
- Linking a Mac to a website account, syncing, and revoking a device.
- Deleting a website account and its data, because the instance is public.

Out of scope for now: teams and sharing, reports and export, billing rates, idle detection, reminders, email and password login, offline use of the website, Windows, Linux and mobile apps, live push between devices, purging deletion markers, code signing and notarization, a Homebrew cask, and command-line control.

## 5. Data model

The same three entities exist in the Mac app's SQLite database and in Postgres.

All ids are UUIDv7, generated by whichever side creates the row. All times are UTC instants; each UI displays them in its own time zone.

**Project**: `id`, `name`, `color`.

**Tag**: `id`, `name`.

**TimeBlock**: `id`, `title` (may be empty), `notes`, `projectId` (nullable), `tagIds` (array of tag ids), `startAt`, `endAt` (null means the timer is running).

Every row also carries:

- `updatedAt`: when the row was last edited.
- `deletedAt`: null, or when the row was deleted. Deleted rows are kept as markers so a deletion can reach other devices.

Side-specific columns:

- **Mac only:** a `dirty` flag per row, and a one-row `sync_state` table holding the server URL, the last `cursor`, and `lastSyncedAt`. `tagIds` is stored as JSON text. These exist from phase 1 and stay unused until phase 3.
- **Server only:** `userId` on every row, and `rev`, a number assigned from one global sequence on every write.

**Device** (server only, phase 3): `id`, `userId`, `name`, `keyHash`, `createdAt`, `lastSeenAt`, `revokedAt`. The API key itself is shown to nobody and stored only as a hash.

Rules, enforced on both sides:

- `endAt`, when set, must be after `startAt`.
- There is at most one running block per database on the Mac and per user on the server.
- Blocks may overlap; the calendar shows them side by side.
- A block that references a deleted project or tag simply shows without it.

## 6. Architecture

```
better-hours/
  apps/
    mac/               Swift app: main window, menubar, LocalStore, SyncEngine
    web/               Vite + React client
    server/            Hono API, Better Auth, Prisma, sync endpoint
  packages/
    shared/            zod schemas and TypeScript types for web and server
  fixtures/            JSON test cases both the Swift and TypeScript suites must pass
```

```
 Mac app                                Website (browser)
 ┌──────────────────────────────┐       ┌──────────────┐
 │ Main window + menubar        │       │ React UI     │
 │ LocalStore ── SQLite         │       └──────┬───────┘
 │ SyncEngine (only if linked)  │              │ REST, session cookie
 └──────┬───────────────────────┘              │
        │ POST /api/sync, API key              │
        └──────────────┬───────────────────────┘
                       ▼
                Hono server ── Prisma ── Neon Postgres
```

The Tauri design had one `TimeStore` interface with two implementations so one UI could run on both sides. That interface is gone. There are now two UIs in two languages, and each has exactly one data path: the Mac app talks to `LocalStore`, and the web client talks to the REST API. What the two sides share is the data model, the REST and sync contracts, and the fixtures.

### Mac app

`LocalStore` is a concrete type over a GRDB database queue. Tests run it against an in-memory database, so no protocol is needed.

```swift
final class LocalStore: Sendable {
    func blocks(in range: DateInterval) async throws -> [TimeBlock]
    func runningBlock() async throws -> TimeBlock?
    func save(_ block: TimeBlock) async throws            // create or update by id
    func deleteBlock(id: UUID) async throws

    func startTimer(seed: TimerSeed?) async throws -> TimeBlock  // stops any running block in the same transaction
    func stopTimer() async throws -> TimeBlock?

    func projects() async throws -> [Project]
    func save(_ project: Project) async throws
    func deleteProject(id: UUID) async throws

    func tags() async throws -> [Tag]
    func save(_ tag: Tag) async throws
    func deleteTag(id: UUID) async throws

    func changes() -> AsyncStream<Void>                   // one stream per caller; fires after any write, local or pulled by sync
}
```

- The methods are async because database work runs off the main thread. Views read from observable view models that reload on `changes`, so view code stays synchronous.
- Every write sets `updatedAt` and `dirty` in the same transaction as the data change.
- The main window and the menubar popover share one `LocalStore`, so they stay in step through `changes` with no extra messaging.
- Day and week totals are pure functions over a list of blocks. They clip blocks that cross midnight and count a running block up to the current time.

### Server

- `GET /api/blocks?from=&to=`, `PUT /api/blocks/:id` (create or update), `DELETE /api/blocks/:id`, and the same three for `/api/projects` and `/api/tags`.
- `GET /api/timer`, `POST /api/timer/start`, `POST /api/timer/stop`. Start and stop are single transactions, so the one-running-block rule holds for web requests too.
- `POST /api/sync` for linked Macs (section 8).
- `/api/auth/*` served by Better Auth.
- Every write, from the website or from sync, takes a per-user lock and assigns the next `rev`. For website writes the server sets `updatedAt` from its own clock.

The web client is a static build served from the same domain as the API, so the session cookie is first-party.

## 7. Timer behaviour

- **Start** creates a block with `startAt = now` and `endAt = null`. If a block is already running it is stopped first.
- **Stop** sets `endAt = now` on the running block.
- **Continue** starts a new block seeded with the title, project, and tags of the most recently ended block. It does not stretch the old block across the gap, so the calendar stays truthful.
- **New** starts a blank block. Details are added later from the calendar or the popover's title field.
- The running block appears on the calendar growing toward the current time.

## 8. Linking and sync (phase 3)

### Linking a Mac

1. In Settings the user clicks "Connect to website". The app generates a random verifier and opens the browser at `/link?challenge=<hash of verifier>&name=<Mac name>`.
2. The website asks the user to sign in if needed, then to approve the device.
3. The website redirects to `betterhours://link?code=<one-time code>`, which opens the app.
4. The app posts the code and the verifier to `POST /api/devices/exchange`. The server checks them, creates the Device row, and returns the API key once.
5. The app stores the key in the macOS Keychain and runs a first sync.

The key never appears in a URL. The code is single-use and expires after a few minutes. The verifier stops another app that intercepts the `betterhours://` link from using the code.

The website lists linked devices with their last-seen time and lets the user revoke one. A revoked key gets a 401; the app then stops syncing, keeps all local data, and shows "Disconnected" in Settings.

### First sync

Local rows and account rows are merged by id. Because ids are generated independently, a Mac with existing data linked to an account with existing data ends up with both sets. Projects and tags with the same name on both sides are not merged in this version; the user ends up with two and can delete one.

Unlinking from Settings deletes the key and keeps local data. Linking afterwards to a different account uploads that local data into the new account, so Settings warns before doing it.

### Sync call

```
POST /api/sync        Authorization: Bearer <API key>
request:  { cursor: string | null, changes: { projects: [], tags: [], blocks: [] } }
response: { cursor: string,        changes: { projects: [], tags: [], blocks: [] } }
```

**Server, in one transaction:**

1. Take the per-user lock, so `rev` values for one user become visible in order and a pull can never skip a row.
2. For each pushed row: accept it if the row is new or its `updatedAt` is later than the stored one, otherwise ignore it. An `updatedAt` in the future is clamped to the server's current time. Each accepted row gets the next `rev`.
3. If the user now has more than one running block, keep the latest-started one running and end each older one at the start of the next. Each row changed this way gets a new `updatedAt` and a new `rev`, so every device receives the repair and none overwrites it.
4. Return every row for the user with `rev` greater than the request's `cursor`, and the new `cursor`.

**Mac:**

1. Collect all rows with `dirty = 1` and send them with the stored cursor.
2. For each returned row: overwrite the local row, unless the local row is dirty and has a later `updatedAt`.
3. Clear `dirty` on each sent row whose `updatedAt` has not changed since it was sent.
4. Store the new cursor and `lastSyncedAt`, then fire `changes`.

**Triggers:** at launch, every 20 seconds, when a window or the popover gains focus, two seconds after a local write, and from "Sync now". Only one sync runs at a time. A sync with nothing to send and nothing new is one small request.

**Website freshness:** the web client refetches the visible range and the running timer every 20 seconds and on window focus, which is how it sees changes from a Mac.

**Known limits, accepted for this version:** if the same block is edited on two devices between syncs, the later edit replaces the earlier one entirely. "Later" is judged by device clocks for Mac edits, so a badly wrong clock can win unfairly. Changes take up to about 20 seconds to appear on the other side.

## 9. Auth and accounts (phase 2)

- Better Auth with Google as the first provider and GitHub as the second. There is no email and password login.
- Sessions are stored in Postgres through the Prisma adapter and carried in a first-party cookie.
- An account is keyed by provider identity. Signing in with Google and later with GitHub using the same email creates one account only if Better Auth's account linking is switched on; this version leaves it off, so they are two accounts.
- Every server query is filtered by the session's or the API key's `userId`. The sync endpoint ignores any `userId` in the payload.
- A user can delete their account. This removes their blocks, projects, tags, devices, and sessions.
- The public instance needs basic abuse limits: a per-user request rate limit and a cap on rows per sync call.

## 10. Screens

The visual design lives on the design canvas: https://claude.ai/artifact/3BimDMZyzYb9TD6ByckdKF. The "App design" page has every Mac screen in light and dark and a sheet of component states. The "Brand" page has the logo, colours, type, spacing, and corner radii.

**Main window.** A toolbar with week navigation, a Today button, and the Week/Day switch. A timer bar with the title field, project, elapsed time, Start or Stop, and today's and this week's totals. The calendar grid with a total under each day name. Drag on empty space to create a block (snapped to 5 minutes), drag or resize to change it, click to open the editor.

**Block editor.** Title, project picker, tag picker (create a tag by typing a new name), start and end, notes, a duration readout, and Delete, Cancel, Save.

**Projects and tags.** Rename, recolor, and delete projects; rename and delete tags. Each project shows its hours for the week.

**Menubar popover.** The bar shows the glyph, plus the running block's elapsed time as `h:mm` while a timer runs. The popover shows the running block with Stop, or the last block with Continue and New, then today's total, "Open Better Hours", and Quit.

**Settings (phase 3).** Server URL, "Connect to website", connection status with the last sync time, "Sync now", and "Disconnect".

**Website.** The same calendar, editor, timer bar, and projects and tags screens, plus sign-in, a devices page, and account deletion. It follows the same colours, type, and component states as the Mac app.

Closing the Mac main window hides it; the app keeps running in the menubar.

## 11. Error handling

- **Mac writes** never touch the network, so they fail only on a local database error, which is shown as a blocking alert.
- **Sync failure:** Settings and the popover show the error and the last successful time; the next trigger retries. Local data is never discarded because of a failed sync.
- **Website:** edits apply optimistically; on a failed request the change rolls back and a message appears.
- **Validation:** the server validates every row with the shared zod schemas and rejects the whole sync call if any row is malformed, so a sync is all-or-nothing.

## 12. Testing

- **Fixtures:** JSON cases in `fixtures/` for day totals (including midnight clipping and a running block), the last-edit-wins merge, and the single-running-timer repair. The Swift test suite and the TypeScript test suite both load and pass the same files. This is what keeps two implementations of the rules from drifting.
- **Mac unit tests:** `LocalStore` against an in-memory database; the sync engine against a stubbed HTTP client.
- **Server integration:** the REST and sync endpoints against a test Postgres, simulating two devices and a browser: both-create, edit conflict, delete on one and edit on the other, two running timers, a stale cursor, a revoked key.
- **Manual checklist:** menubar time ticking with the window hidden, popover open and close, light and dark themes, the link flow from Settings through the browser and back, offline tracking then sync.

## 13. Open questions

- **Minimum macOS version.** 14 is my default; an older target rules out some SwiftUI APIs.
- **Web calendar component.** I have not confirmed whether FullCalendar v7 and its shadcn theme are stable, or the licence of its standard plugins.
- **Same-name projects and tags on first sync.** This version leaves duplicates; merging by name is the alternative.
- **Mac distribution.** An unsigned build is blocked by Gatekeeper on first launch and has to be allowed by hand in System Settings.
- **Domain and instance name** for the public website.
